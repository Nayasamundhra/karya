# Karya backend - pinned runtime dependency closure.
#
# WHY THIS FILE EXISTS
# ====================
# `pyproject.toml` declares ranges (`fastapi>=0.115`), which is right for a
# library and wrong for a deployment: two builds a week apart would install
# different code. This file pins every package in the runtime closure - direct
# dependencies and their transitive ones - so `pip install --constraint
# constraints.txt .` resolves identically every time.
#
# The Dockerfile uses it. Local development deliberately does not, so that a
# broken upstream release is discovered here rather than in production.
#
# HOW IT WAS PRODUCED
# ===================
# In a clean virtualenv with nothing else installed:
#
#     python -m venv /tmp/lock && /tmp/lock/bin/pip install .
#     /tmp/lock/bin/pip freeze --exclude-editable
#
# so it is the resolver's own answer, not a hand-curated list. Regenerate the
# same way after changing a dependency in `pyproject.toml`, and run the test
# suite against the result before committing it.
#
# HONEST LIMITS
# =============
# * No hashes. `--require-hashes` would be stronger - it defends against a
#   tampered index - but hashes must cover every platform wheel a build might
#   pull, and this project has no lock tool to maintain them. Version pinning is
#   the guarantee on offer; it is not supply-chain integrity.
# * Resolved on Windows/CPython 3.12. The versions are platform-independent, but
#   a package that resolves differently per platform could differ on Linux.
#   Constraints only bound what pip installs, so an unused entry is ignored
#   rather than being an error.
# * Pins are not security updates. Review them deliberately - see
#   docs/PRODUCTION.md - rather than assuming a pinned tree stays safe.
#
